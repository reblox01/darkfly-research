Design brief · Researched 23 Oct 2026

DarkFly, rebuilt: fewer tools, real installs.

Deep research into the modern tool-installer landscape, practitioner blogs and hacker-community benchmarks, plus a hands-on baseline test of the current version in a VM. The conclusion is blunt: the classic DarkFly model is dead, and practitioners have already replaced it. DarkFly v4, Tool-X, AllHackingTools, Lazymux and Katoolin all share one design, a numbered menu over hundreds of hard-coded repos, installed with git clone and Python 2, with no pinning, no uninstall and no verification. They share the same failure modes too.

The replacement model, agreed by Kali, Black Hills Information Security, ProjectDiscovery, SpecterOps and Exegol: a small curated catalog, installs through a real package manager wherever possible, and every install pinned, recorded and reproducible. This page is the blueprint for building DarkFly that way.

01 / THE VERDICT

Why the numbered menu died

Every classic installer fails the same five ways. Each one is documented, not opinion, and each maps to a design rule for the new version.

The five failure modes

  • Python 2 end-of-life. It killed Katoolin and DarkFly v4 outright; v4's own README admits "the DarkFly tools on linux does not working", and updating means a full reinstall that deletes the old files.
  • Dead and renamed upstreams. CrackMapExec was archived in 2023 and replaced by NetExec. Every catalog still pointing at the old name silently broke, and instantly dates itself.
  • Host breakage. Katoolin adds Kali's rolling repos to a stable Ubuntu or Mint host with no safety checks, leading to "unresolvable dependency conflicts which will finally break" the system.
  • Opaque trust leaps. A clone plus a setup script is arbitrary code execution, repeated hundreds of times. AllHackingTools even fetches a remote config token from GitHub before its menu opens.
  • No record of anything. No pinning, no manifest, no uninstall. Nobody can say what was installed, at what version, or how to remove it.

Sources: DarkFly v4 repo · Linux Mint forum, Katoolin breakage · AllHackingTools remote config check

The three rules of the new model

  • Curate, don't accumulate. Kali curates through metapackages and a top-10 list. BHIS peer-reviewed cheatsheets cover only about 9 core tools. EC-Council's beginner answer is 4 tools plus a lab platform.
  • Install through real package managers. Signed apt/pkg packages, isolated pipx environments, go install, or a vendor's own manager like ProjectDiscovery's pdtm. Not raw clones.
  • Pin, record, reproduce. Exegol pins an image generation so a retest six months later runs the same stack. AD playbooks record the tool version alongside the evidence. A manifest file does the same job on a phone.

Sources: Kali metapackages · BHIS cheatsheets · Exegol on reproducibility

03 / IN PRACTICE

What practitioners actually use

Cyber blogs, cheatsheets and community benchmarks converge on the same small core, organised by workflow phase rather than alphabetically. Kali 2025.2 even reorganised its own menu around MITRE ATT&CK.

Depth on a few tools

Black Hills Information Security's Offensive Tooling Cheatsheets went through "careful technical peer review" and "double- and triple-checking syntax", and cover only nine tools: Burp Suite, DNS Triage, EyeWitness, GraphRunner, Hashcat, Impacket, Netcat, Nmap, Wireshark. They moved from print to updatable digital "as tools and technologies shift".

blackhillsinfosec.com

The 80% answer is tiny

EC-Council's 2026 beginner toolkit is deliberately minimal: Kali + Nmap + Burp Community + Metasploit + HackTheBox / TryHackMe, which "covers 80% of what professional pentesters use". Meanwhile Kali's own kali-tools-top10 is Nmap, Wireshark, Burp, sqlmap, Metasploit, Hydra, John, Responder, NetExec and Aircrack-ng.

eccouncil.org · kali.org

Resources are a catalog too

SecLists (74,307 ★) is maintained by named people, Daniel Miessler, Jason Haddix, Ignacio Portal and g0tmi1k, so a tester can "pull this repository onto a new testing box and have access to every type of list that may be needed". Wordlists and references like PayloadsAllTheThings and HackTricks carry the same value as tools, at a fraction of the install risk.

04 / THE NEW CATALOG

Four tiers, every entry accounted for

The proposed catalog, built from the research: the timeless core, the modern layer classic DarkFly lacks entirely, resources treated as first-class entries, and a small clearly-labelled emerging tier. Filter by tier or search. Backend is how the new installer would install it; Termux flags what is honest to promise on a phone.

Explicitly excluded, by design: SMS/call bombers and spam tools (v4's headline "7 SMS spam tools"), Gmail bombers, webcam-phishing and DDoS-Ripper-style entries, and any tool whose upstream is archived with a named successor. Their absence is a differentiator, and the README should say so.

05 / BENCHMARKS, WITH THEIR CAVEATS

What the blogs claim, and what survives scrutiny

Practitioner comparison numbers are useful for one thing: deciding which tools belong side by side in the catalog. They are not catalog facts, and the new project should never quote them as such.

Full port scan, one host, all 65,535 ports

Gigabit LAN, Kali 2025.1. Log scale, seconds to finish. The lesson: ship Nmap and RustScan, and document the combined workflow. Speed without service detection is not a finished scan.

Source: securityelites.com, self-reported. A comparative study reaches the same qualitative split: Nmap is the depth/NSE standard, Masscan/ZMap are internet-scale speed with accuracy trade-offs (Latinoware study).

Web fuzzers, local throughput

Requests per second in one local benchmark. On real internet targets "the difference is minimal", so the catalog carries all three with a one-line "use when" each. Wordlist choice dominates results, which is why SecLists is a Tier 2 entry.

Source: securityelites.com, self-reported, local targets only.

Hashcat vs John: the numbers war

One SEO benchmark pits Hashcat on an RTX 4090 against John on a 16-core CPU: NTLM 164,000 vs 8,200 MH/s, MD5 68,000 vs 4,100 MH/s. HackMag's practical testing counters that benchmarks "outperform actual results by several times" and are "not really stable". A careful comparison concludes the two are "complementary, not competitors": Hashcat for raw hashes and Wi-Fi, John for files and no-GPU machines.

Catalog decision: on Termux there is no GPU path that matters, so John is the sensible default and Hashcat is a low-priority, warn-heavy entry. GPU MH/s figures never appear in the catalog.

SEO benchmark · HackMag scepticism · techearl, complementary view

Caido vs Burp: the trending challenger

A practitioner head-to-head on the same target: Caido's scanner plugin found ~400 issues / 12 unique, Burp Scanner over 1,000 / 17 unique. Caido has no built-in scanner or crawler (plugins fill the gap) but is Rust, lightweight, with a modern UX. Kali packaged Caido in 2025.3.

Catalog decision: Burp and ZAP stay the reference; Caido is listed as "emerging, laptop-class", not as a Termux install.

afine.com practitioner test · lumicalabs feature table

Benchmark hygiene. The scanner, fuzzer and cracker numbers above come from low-authority, SEO-driven sites with no published raw data, hardware variance or repeat runs, and HackMag actively contradicts the cracker headlines. Treat them as directional practitioner folklore. And one genuine gap: no head-to-head installer benchmark exists anywhere (install time, failure rate, uninstall cleanliness for DarkFly vs Tool-X vs pdtm vs Kali metapackages). Publishing the first honest one is a credibility moat, see differentiator 8.
06 / THE BLUEPRINT

Eight differentiators, ranked by impact vs effort

What would make the new version genuinely different from the old one and every clone, in the order the research says to build them.

1

Real installs with a manifest

Install, update, uninstall and list-installed, all backed by an installed.json manifest recording tool, version or commit, backend, files created and dependencies. v5's core gap is that it installs nothing; pdtm proves users value install-all / update-all / list-outdated / remove in one tool. The manifest is also what makes every other safety feature possible.

Impact: HighEffort: Medium
2

A curated catalog of 60–100, with maintenance metadata

Kali top-10 plus the ProjectDiscovery suite plus the AD set is the product. Every entry carries status (maintained / stale / archived), successor_to and last_verified, turning link-rot from a silent failure into visible data. Curation is ongoing work: budget for it, and automate the checks in CI.

Impact: HighEffort: Medium
3

Backend delegation, in a strict priority order

Stand on signed and isolated channels instead of owning 100 bespoke install scripts. Delegate ProjectDiscovery tools to pdtm and Kali-packaged tools to apt. Record which backend was used so update and uninstall reverse the right thing. The ladder is specified below.

Impact: HighEffort: Medium
4

Dry-run, pre-flight, resumable installs

--dry-run prints every command, download size and file to be written, and executes nothing. Installs are staged and journaled so an install killed mid-way (signal 9, battery, network) resumes or rolls back cleanly. Re-running install on an installed tool is a no-op success. Try it in the simulation.

Impact: HighEffort: Low–Med
5

Search and a fuzzy picker, with full CLI parity

v5 has no search, and numbered menus collapse well before 80 tools. darkfly search nuclei, scriptable subcommands with --dry-run, --yes and JSON output, Rich tables, and a questionary picker for interactive use, all on the same code path. Stay in Python: a Go rewrite would orphan the v5 codebase and shrink the Termux contributor pool.

Impact: Med-HighEffort: Low
6

A health doctor: darkfly doctor

Checks Termux source and mirror sanity, Python version, free storage, the phantom-killer risk, whether each installed tool's binary still runs, and whether its upstream has been archived. It turns "it broke" GitHub issues into self-service diagnosis, the same issue pattern that produced v5's open "how do I use it" reports.

Impact: Med-HighEffort: Low
7

A resources catalog, not just tools

SecLists subsets, PayloadsAllTheThings, HackTricks, GTFOBins: resumable, checksummed downloads with size choices (small bundles on Termux, full on Linux; rockyou as a verified download, never bundled). Data, not code, so the install risk is minimal and the value is daily.

Impact: MediumEffort: Low
8

Catalog CI and a published honesty benchmark

CI validates the catalog schema, checks every upstream URL resolves and is not archived, and smoke-tests --dry-run for every entry, catching link-rot continuously. Then publish measured time-to-install, failure rate and uninstall cleanliness for the top-20 catalog on a named Termux device and a named Linux VM. No competitor can copy that with a banner change.

Impact: MediumEffort: Medium

Backend priority ladder

1apt / pkgSigned package from Termux or Debian/Kali repos. Signatures verified by the package manager itself.
2vendor binaryPublisher's release binary for the exact OS/arch, sha256-verified where upstream publishes one, installed atomically (temp dir, then rename into place).
3pipx / go installPinned version. pipx gives each Python tool its own venv, never needs sudo, and makes uninstall reliable. This alone fixes the number-one breakage class in classic installers.
4git clone @pinLast resort only, pinned to a commit, with a visible warning. Never an unpinned clone of a moving branch.

Modelled on Homebrew's reviewed formulae and bottles, mise's "prefer backends that install a publisher's release directly", and cargo-binstall's checksum-verified atomic installs. Sources in Sources.

The catalog record (minimum viable schema)

{
  "id": "netexec", "name": "NetExec",
  "aliases": ["nxc"],
  "description": "Network service exploitation /
    AD assessment (successor to CrackMapExec)",
  "categories": ["ad", "post-exploitation"],
  "license": "…", "homepage": "…",
  "status": "maintained",
  "successor_to": "crackmapexec",
  "platforms": { "termux": true, "linux": true,
    "gui_required": false },
  "size_mb_estimate": 120,
  "last_verified": "2026-10-23",
  "install": { "backend": "pipx",
    "package": "git+https://…@<pin>" },
  "run": "nxc"
}

One plain-JSON record per tool, in-repo and diff-able in pull requests. No obfuscated catalog, ever: that was a v4 failure mode, not a style choice.

Safety checklist: ship-blockers, not nice-to-haves

  • No curl | bash, no remote code at startup, no obfuscated catalog. The catalog is plain JSON in the repo. A piped script "can serve different content when it detects a pipe", and package-manager packages are cryptographically signed while piped scripts are not signed at all.
  • Every entry carries provenance: canonical upstream URL, license, maintainer or org, a last_verified date and a maintenance status. Archived tools are auto-flagged and successors linked (CrackMapExec → NetExec).
  • Pin everything; verify sha256 or signatures where upstream provides them; HTTPS only.
  • Dry-run before any install, and explicit confirmation for heavy (over 500 MB) or privileged installs.
  • Never root, never sudo on Termux, never add foreign APT repos (the Katoolin rule), never modify anything outside the tool's own prefix.
  • Isolated per-tool installs (pipx venvs, a dedicated directory per clone) plus a manifest of everything created, so uninstall is complete and list-installed is truthful.
  • Exclude bomber, spam and DoS-for-fun entries. GitHub explicitly permits dual-use security technology and assumes positive intention, but not content "in direct support of unlawful attacks"; phishing and social-engineering tools sit behind an offensive category with a lawful-use notice at install time.
  • README carries an educational / authorised-use disclaimer, plus a SECURITY.md contact and contribution rules requiring a working install test on Termux and Linux for every new entry.

Policy sources: GitHub active malware or exploits policy · GitHub acceptable use policies · Why curl | bash is dangerous

08 / TERMUX REALITIES

The platform decides what is possible

Most "installer randomly died" reports are platform facts the installer ignored. The new design treats these as constraints, not surprises.

Get Termux from F-Droid or GitHub

The Play Store build was abandoned in 2020, is frozen at 0.101, and points to dead repository mirrors. APKs and all add-ons must come from the same source, because they are signed with different keys; mixing them fails with INSTALL_FAILED_UPDATE_INCOMPATIBLE. A current Play listing for Android 11+ exists but is still in development with missing functionality.

Signal 9 is the #1 killer

Android 12+'s Phantom Process Killer terminates Termux children past roughly 32 phantom processes or under heavy CPU: the infamous [Process completed (signal 9)]. User-side fixes exist (Android 14+ Developer Options, or ADB device_config settings), but the design consequence is on us: resumable, journaled, low-parallelism installs are mandatory, with a pre-flight warning before heavy installs.

Everything lives under $PREFIX

Home is /data/data/com.termux/files/home, binaries live under $PREFIX, and there is no FHS, no systemd and no root. Desktop glibc binaries generally won't run on Android's Bionic libc, the classic "No such file or directory" for a file that exists. Storage permission is opt-in via termux-setup-storage; the installer must work fully without it.

pkg is APT, and that is a feature

pkg wraps APT with mirror selection (health-checked, weighted), a cache-freshness check and a refusal to run as root. Official repos are signed via termux-keyring. A good installer shells out to pkg and lets it verify signatures instead of reimplementing downloads. Dead mirror? The fix users need is termux-change-repo, and doctor should say so.

Python 3 only, pipx always

Python 2 is legacy and is the single reason v4-era tools fail on a fresh install. Modern Python also blocks global pip install ("externally-managed environment"), the exact wall a practitioner hit installing NetExec on HTB Pwnbox, and solved with pipx. The whole tool targets Python 3.10+, and every Python tool it installs is pipx-isolated.

What breaks most often

In order: stale Play-Store Termux with dead mirrors; dead or slow mirrors failing pkg update; Python 2 scripts; global pip dependency conflicts; signal-9 kills mid-build; desktop-glibc or x86 binaries on arm64; tools needing root, monitor mode, systemd or a GUI; and multi-GB "install everything" runs exhausting phone storage (AllHackingTools alone claims ~2.2 GB).

Sources: Termux package management (wiki) · Andronix, phantom process killer · NetExec via pipx on Pwnbox · Termux community: prefer repo packages over installer scripts

09 / TRAPS

Features to refuse, on the record

Each of these sounds like an upgrade. Each is refused or deferred for a stated reason, so the decision survives the next "why don't we just…" conversation.

An "install all 530" button

Multi-GB, hours long, maximal signal-9 and storage failure, and most entries will be stale. Kali can offer kali-linux-everything only because a real distro repo stands behind it. A clone-script cannot honour it.

Docker, Exegol or Nix as the Termux mechanism

No usable Docker daemon or Nix store model on unrooted Android, and both are storage- and complexity-heavy. Copy their pinning, manifest and isolation principles only.

A full-screen TUI or Go rewrite first

It delays the one thing that matters, working installs, and a Go/Bubble Tea rewrite orphans the Python v5 code and its contributor pool. Textual can come later as an optional front-end.

On-device promises that need a desktop

GUI tools, the BloodHound server, GPU Hashcat and monitor-mode Wi-Fi need a desktop, a database, a GPU or special hardware. List them as "desktop companion" info entries; never fake-install them on Termux.

An autonomous AI agent in v1

Kali is only now adding MCP/AI servers, and practitioner sources call LLM tooling "still early, still maturing". An autonomous executor multiplies the safety surface: prompt-driven arbitrary commands and API-key exfiltration. Later, opt-in and dry-run-gated, at most.

Parallel-download acceleration as a headline

apt-fast-style tricks only speed the download phase and risk mirror or signature shortcuts. Mobile networks and the phantom-killer limit dominate Termux install time anyway.

SMS / DDoS / phishing-bomber categories "for parity"

Policy risk under GitHub's acceptable-use rules, reputational risk, and zero practitioner demand. Their absence is a differentiator.

Winning on tool count

The clone field is saturated with 370-to-530-tool menus. BlackArch shows what a huge catalog actually costs: a distro, a keyring and maintainers per package. Curation is the moat; count is the trap.

10 / OPEN QUESTIONS

What the research could not verify

Marked plainly, because a brief that hides its gaps produces a README that repeats them.

Tool-X's real star count and last-commit date are unknown. Tutorials from 2020–2025 are abundant, but no primary GitHub fetch for the canonical repo was obtained, and its clone URL drifts between authors. Do not publish a Tool-X star number without a fresh primary fetch.
Reddit and Null Byte are second-hand only. Index searches for r/netsec and r/Pentesting returned aggregators, not primary threads, and no direct Null Byte installer article was retrieved. Community sentiment in this brief is reported as consensus, and neither should be cited as primary evidence in marketing copy without a direct fetch.
v5's tests/CI: substantive or not? The research flagged a discrepancy: v5's README lists a tests/ directory, workflows and pytest instructions, against the assumption of "no tests, no CI". The VM baseline for this brief confirms tests exist and pass (3/3), but whether CI runs them on every push was not verified in-repo.
All speed benchmarks are folklore-grade. Self-reported by low-authority sites, no raw data, no replication, and partly contradicted by HackMag's testing. Directional only, never to be copied into the catalog as fact.
No installer benchmark exists. Nobody has published install time, failure rate or uninstall cleanliness for DarkFly vs Tool-X vs pdtm vs Kali metapackages. Any such numbers in a future README must be measured (differentiator 8), not sourced.
GitHub figures are index readings, not live-verified. The research browser could not resolve github.com in its first pass, so star and fork counts are point-in-time web-index readings from 23 Oct 2026 and will drift.
